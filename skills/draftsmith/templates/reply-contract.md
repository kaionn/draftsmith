# designer 出力契約（reply contract）

designer の成果物は以下の 5 要素で構成する。要素 1〜4 は必須（該当なしでも見出しを立てて
「なし」と明記する）、要素 5 は閾値該当時のみ。main はこの契約への準拠を監査の入口で
機械的にチェックし、要素が欠けた成果物は内容を読む前に差し戻す。

## 二層構造: ファイル本体と return 要約

成果物は「ファイル本体」と「return 要約」の二層に分ける。main が return 全文を再出力して
永続化する構造（1 run で 50K 字超の再書き出し）を無くすため。

- **ファイル本体**: designer が main の渡した `designer-return.md`（規約 path は
  `~/.local/state/draftsmith/runs/{repo}/{task-slug}/designer-return.md`）へ全文を Write する。
  先頭行は `<!-- requirements-sha256: {main が渡した要件書の digest} -->`。続けて 5 要素を
  `## 要素 1` 〜 `## 要素 5` の見出しで書く（見出し行の先頭は `## 要素 N` で始める）
- **return 要約**: main へ返す本文は「書いた path + 5 要素の見出しごとの行数 + 要素 2・3 の
  全文 + 要素 4 の表」だけ。要素 1（brief 本体）と要素 5 は return へ貼らない
- **機械検査**: main は `scripts/check_reply_contract.py <designer-return.md>
  --requirements <requirements.md>` の結果だけで形式差し戻しを判断し、return 本文を読み込まない。
  検査項目は 5 要素見出しの存在、要素 4 が要件書の全 AC-n を 1 回ずつ含むこと、要素 1 末尾の
  `### 調査済みファイル` 小節の存在、先頭行の digest が要件書の実 digest と一致すること
- **再利用**: 同じ task-slug の `designer-return.md` が既に存在し digest が一致すれば、main は
  designer を再起動せずそのファイルを再利用する。不一致なら再起動する

auditor（`audit.md`）と implementer（`implementer-report.md`）も同じ二層で、ファイル本体を
同じディレクトリへ書き、return は件数・合否の要約だけにする。

## 要素 1: 実装 brief（本体）

implementer が設計判断ゼロで適用できる逐語 brief。品質基準:

- **冒頭に構造ビジュアル 1 点**: brief の先頭に「構造ビジュアル」小節を置き、変更後の
  コードの形を 1 点のビジュアルで示す。読者は人間と auditor（設計の形を編集指示より先に
  検査するための小節）で、implementer への編集指示ではない。形式は見せたいものに合わせて
  1 つだけ選ぶ:

  | 見せたいもの | 形式 |
  |---|---|
  | ファイル・モジュールの責務配分、新規/変更ファイルの配置 | ファイルツリー（変更 `*`・新規 `+` の印付き） |
  | 呼び出し関係・データフロー・シーケンス | Mermaid |
  | 分岐・状態遷移が主役のロジック | 疑似コード |
  | 既存の形は保たれ、変更点だけが焦点 | diff スケッチ（概形でよい。逐語引用は編集指示側の責務） |

  複数形式を併用しない。ビジュアルと編集指示が食い違う場合は編集指示を正とする。
  light レーン（main が brief を直接書く場合）では省略してよい
- **末尾に必須小節 `### 調査済みファイル`**: designer が実際に開いたファイルを 1 行 1 ファイルで
  `path — 確認した事実（file:line）` の形式で列挙する。auditor はこの一覧から読み始め、一覧外を
  開くのは接合面検査に必要な呼び出し元・テストだけに限る（探索の重複を省き、結論の検証で
  独立性を担保する）。空の小節は契約違反。light レーンでは省略してよい
- **編集指示は逐語**: 置換対象コードは実ファイルからの逐語引用。対象はファイル内で一意に
  特定でき、複数の編集指示の範囲が重複しないこと
- **新規ファイルは全文**: 断片やあらすじではなく、そのまま書き込める完全な内容を記載する
- **例外 2 モードは宣言してから使う**（詳細は agents/implementer.md と対になる）:
  - `機械的展開モード` — 同型の置換が 3 件以上あるとき。例示 1 件 + 適用先の完全列挙 +
    差分パラメータ表で表現してよい
  - `仕様委譲モード` — テストコード・ストーリー等に限り、逐語でなく仕様で委譲してよい。
    期待値表 + 準拠すべき既存の兄弟ファイル + モック方針を必ず添える

## 要素 2: 確認事項リスト（提案デフォルト付き）

調査・設計の過程で判断が割れた点を列挙する。各項目に必ず
**「designer の推奨デフォルト + 理由 1 行」** を付ける。
デフォルトなしの丸投げ質問（「どうしますか？」）は契約違反。
自律モードでは main がこのデフォルトを保守的観点で採否判断するため、
デフォルトの質がそのまま自走の質になる。

## 要素 3: 前提崩れ・要件矛盾の報告（別枠）

調査の結果、要件書の前提が事実と食い違っていた場合、または受け入れ基準同士が
矛盾する場合は、確認事項に混ぜず **この別枠** で報告し、代替案を必ず添える。
これが designer が要件を覆せる唯一の経路（要件の無断修正・無断解釈は禁止）。
該当なしなら「なし」と明記する。

## 要素 4: トレーサビリティ表

| 受け入れ基準 | 対応する brief 要素 |
|---|---|
| AC-1 | （brief のどの編集指示・どの新規ファイルが満たすか） |
| AC-2 | … |

要件書の全 AC を行として網羅する。カバーできない AC は「未カバー + 理由」を書く。
黙って行を落とすのは契約違反（`check_reply_contract.py` がこの表と要件書の AC 一覧を機械照合する）。

## 要素 5: mini-ADR（重要判断のみ）

templates/mini-adr.md の閾値に該当する判断があった場合のみ記載する。
該当しなければ要素自体を省略してよい（唯一の任意要素）。
